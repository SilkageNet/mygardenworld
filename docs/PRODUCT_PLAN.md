# mygardenworld 产品计划

更新时间：2026-07-02

本文记录当前项目的产品方向、领域建模和架构重构计划。目标不是小修小补，而是把自动化从“功能开关 + 局部启发式”升级为“任务目标驱动 + 统一库存账本 + 可解释调度”的系统。

本文只记录产品与工程理解，不复制第三方前端资源，也不修改或绕过第三方页面保护脚本。

演进原则：允许合理的破坏性变更。若旧文档、旧策略 JSON、旧 proto/API 形态与更清晰的领域模型冲突，以当前项目目标和新的领域模型为准，不为了兼容旧形态牺牲正确性与可解释性。

## 背景

当前项目是本地优先的 `gardend` 守护进程 + `gardenctl`/Web 控制台架构，已经具备很好的原材料：

- `internal/babigame`：登录、WebSocket、RPC、协议命名空间和静态协议信息。
- `internal/state`：土地、库存、水滴、培育、订单、任务、活动等运行态数据。
- `internal/automation`：当前土地操作决策引擎。
- `internal/runner`：账号生命周期、连接、状态同步、自动化循环和实际 RPC 执行。
- `internal/store`：SQLite 持久化，包括账号、会话、策略、操作日志。
- `internal/apiserver`：Connect/gRPC API。
- `web`：本地控制台。
- `gardencap`/`gardencatalog`：协议捕获、静态表提取和代码生成工具。

现阶段最大问题不是“能不能执行某个 RPC”，而是“系统是否知道为什么执行、为了哪个任务执行、执行后会解锁什么链路，以及哪些资源不能被低优先级动作抢走”。

## 竞品观察

对同类产品的公开前端元信息和字符串做了只读分析。浏览器自动化登录不稳定，且页面存在保护逻辑；本计划不基于第三方资源本地化，也不移除其保护脚本。

可观察到的产品能力包括：

- SaaS 账号层：登录、注册、重置、邀请码、额度、子账号、支付、订单、退款、工单、公告、维护模式、管理员统计。
- 运行编排层：Kubernetes 启停、排队位置、日志轮询、容器状态、节点指标。
- 游戏账号层：添加账号、更新 token/昵称、渠道校验、服务器选择、同步信息、启动/停止、查看日志。
- 自动化设置层：基础、种植、订单、公会、活动、水滴、珍珠、商城、猫/动物、花艺、宫廷订单、居民订单、顾客订单。
- 对我们最有启发的产品概念：
  - 任务优先模式。
  - 先种订单需要的花。
  - 根据任务自动启用对应功能模块。
  - 任务完成后自动恢复原始配置。
  - 指定花艺：优先使用库存，上架不足则制作；花朵不足时配合任务优先种植。
  - 仅提交已培育的花朵。
  - 居民订单、建材订单的单日最大完成次数。
  - 任务优先级。
  - 种植任务队列日志。

核心启发：真正有价值的抽象不是“低库存 / 高价值 / 自选种植模式”，而是“启用的任务产生需求，需求驱动生产，生产驱动种植、浇水、收获、制作、上架、交付”。

## 产品目标

把 mygardenworld 做成一个本地优先、可解释、可持续演进的自动化控制台。它应该能回答：

1. 当前账号启用了哪些目标？
2. 每个目标产生了哪些物品、花朵、花艺、资源需求？
3. 哪些需求已满足、正在生产、被阻塞？
4. 下一步动作是什么？
5. 为什么选择它而不是其他动作？
6. 哪些库存已经分配给高优先级目标，哪些仍可被低优先级动作使用？
7. 执行后状态发生了什么变化？

Web UI 应该像一个操作台，而不是松散设置页。核心界面包括：

- 账号健康状态和连接状态。
- 目标看板和需求图。
- 生产队列：种植、浇水、收获、制作、上架、交付、领奖。
- 库存账本视图。
- 策略编辑器。
- 操作日志：领域、动作、成本、结果、失败原因。

## 当前架构诊断

### 1. Planner 和 Executor 边界不清

早期 `internal/automation.PlanOperations` 只覆盖土地相关操作，真实业务动作容易散落在 runner 的顺序分支里。现在订单、花艺、基础领奖等主要动作已经逐步迁入统一计划对象，runner 也已用 operation registry 承接参数构造和 RPC 执行。这个方向仍需要持续保持，避免新增功能重新变成脚本分支。

- 新动作必须先成为 `PlannedOperation`。
- 参数构造、成本门槛和 RPC 执行登记在同一条执行路径。
- UI 以需求队列、库存账本、操作队列和阻塞汇总展示计划解释。
- runner 只保留编排、资源硬校验和状态回写。

### 2. 种植策略不是目标驱动

当前的低库存、高价值、自选等模式适合作为兜底经济策略，但不适合作为全自动主策略。它们不知道：

- 居民订单缺什么花。
- 顾客订单需要哪些花或花艺。
- 花艺需要哪些原材料花和花瓶。
- 主线、每日、每周、公会、活动任务会产生什么需求。
- 哪些库存已经被统一账本分配给更高优先级目标。

这会导致一个典型问题：系统一直在“合理地种花”，但永远完不成某些居民任务、顾客任务或活动任务。

### 3. 顾客订单与花艺链路不足

居民订单很简单：要求满足就交付。

顾客订单复杂得多：

1. 顾客可能直接要求花。
2. 顾客也可能要求花艺成品。
3. 花艺成品需要特定花朵。
4. 花艺成品还需要对应花瓶能力。
5. 花朵不足时要转成种植需求。
6. 成品制作后要优先分配给顾客订单，不能被花架售卖消耗。

当前代码已经有部分链路，但还不是完整的领域模型。

## 花艺与花瓶数据现状

### 已经掌握的数据

代码层面已经知道花艺制作原材料：

- `internal/state/catalog.go` 中有 `FlowerArtRecipe`。
- `FlowerArtRecipeByID(artID)` 从静态表 `c_flowerArt` 解析配方。
- 一个配方包含：
  - `ArtID`：花艺成品 ID。
  - `VaseID`：制作 RPC 使用的花瓶组 ID。
  - `Flowers`：所需花朵 ID 列表。
  - `Level`：可制作等级门槛。
  - `SaleValue`：售卖价值，用于排序。
- 当前实现还包含一次 ID 转换：客户端静态表里的展示花瓶/花朵 ID 与 RPC 使用的花瓶组/真实花朵 ID 不完全一致，代码已根据捕获样本校正。

代码层面也已经在使用这些数据：

- 顾客订单缺花艺时，`tryCraftCustomerOrderArt` 会查配方并调用 `flowerArt.makeFlowerArt`。
- 花架空位需要补货时，`tryStockFlowerRack` 会选择库存花艺，或者尝试制作可制作的高价值花艺。
- 查询接口会把顾客订单中的花艺需求展开成对应花朵需求，便于 UI 展示。

### 目前缺失的数据

当前系统还没有把“自己是否解锁了某些花瓶”建成一等状态：

- 协议 schema 已经知道 namespace `102` 是 `vaseTot`，其中 `IVaseTot.vaseMap` 代表花瓶集合。
- `internal/babigame/protocol_catalog.go` 把 `102` 标记为已知但未建模。
- `internal/state.State.applyTop` 当前解析 100、7、114、101、109、104、105、22、117、116、119、129，没有解析 102。
- 制作花艺应检查花朵库存、配方花朵是否已培育、以及 `VaseID` 是否已解锁；`c_flowerArt.lvl` 是花艺配置等级，不作为玩家等级门槛。

结论：我们“了解配方原材料”，但还“不可靠地了解账号实际花瓶能力”。这会造成两个风险：

- planner 可能认为某个花艺可制作，但 RPC 因花瓶未解锁失败。
- 顾客订单可能被判断为只缺花朵，实际上还缺花瓶能力。

### 应补齐的模型

建议新增：

```go
type VaseView struct {
    VaseID int32
    UTimeMs int64
    CTimeMs int64
}
```

状态层能力：

- 解析 namespace `102.0.<vaseId>` 或捕获确认后的实际结构。
- 提供 `UnlockedVases() map[int32]VaseView`。
- 提供 `HasVase(vaseID int32) bool`。
- 将 `102` 标记为 modeled namespace。

规划层能力：

- `RecipeAvailability(recipe)` 同时检查等级、花瓶、花朵库存和账本可用量。
- 顾客订单需求展开时，花艺需求应扩展为：
  - 成品花艺需求。
  - 若无库存成品，则生成制作需求。
  - 制作需求再展开为花朵需求与花瓶能力需求。
  - 花瓶未解锁时，标记为 blocked，并在 UI 给出明确原因。

## 目标架构

### 1. Domain State：只表达事实

`internal/state` 保持为事实层和派生读模型：

- 土地与作物状态。
- 库存和资源。
- 培育状态。
- 居民订单。
- 顾客订单。
- 花艺货架。
- 花艺库存。
- 花瓶解锁状态。
- 任务和活动进度。
- 静态表查询。

State 不直接决定“下一步做什么”，而是回答领域问题：

- 当前有哪些订单？
- 每个订单要求什么？
- 哪些需求已满足？
- 哪些需求缺库存、缺花瓶、缺培育、缺等级？
- 当前库存扣除账本分配后还剩多少？

### 2. Demand Engine：需求生产器

在 `internal/automation` 下引入需求模型：

```go
type Demand struct {
    ID       string
    Source   DemandSource
    ItemID   int32
    Count    int32
    Have     int32
    Allocated int32
    Available int32
    Priority int32
    Reason   string
}

type DemandSource struct {
    Category string
    Domain   string
    EntityID string
    Label    string
}
```

需求生产器包括：

- 居民订单生产器：订单要求转成花朵需求。
- 顾客订单生产器：直接花朵要求转成花朵需求。
- 顾客花艺生产器：缺成品则生成制作需求，制作需求展开为花朵/花瓶需求。
- 主线任务生产器：任务要求转成花朵或动作需求。
- 每日/每周任务生产器：根据任务类型生成可执行目标。
- 公会、活动等后续生产器；宫廷/组团订单已进入目标生产器和统一账本。

### 3. Inventory Ledger：统一库存账本

在选择动作前先做本轮本地账本分配：

- 为高优先级订单分配花朵。
- 为顾客订单分配花艺成品。
- 缺少成品时再展开制作材料需求。
- 花架、制作、交付都从同一份账本读取可用量。
- 金币、元宝、材料、水滴等成本先在 planner 中形成 `CostGate`，runner 执行前基于同一 gate 类型做最终硬校验。

这样可以避免低优先级动作抢走高优先级目标资源，例如花架卖掉顾客订单需要的花艺。

### 4. Goal Planner：目标规划器

新的 planner 应按以下流程工作：

1. 从 policy 构建启用目标。
2. 从目标构建需求。
3. 应用库存账本分配。
4. 构建候选操作。
5. 按优先级、解锁价值、可执行性、成本和阻塞原因打分。
6. 返回下一步操作和完整候选队列。

低库存、高价值、自选种植仍保留，但降级为“需求满足后的兜底策略”。

### 5. Operation Registry：统一操作注册表

每个动作都应该有同一种描述形态：

```go
type OperationSpec struct {
    Kind     string
    Category string
    Domain   string
    Action   string
    Label    string
    Mutating bool
    Execute  OperationExecutor
}
```

逐步把 `tickDomainWork` 中的分支迁移成统一操作：

- `farm.harvest`
- `farm.plant`
- `farm.water`
- `order.resident.submit`
- `order.customer.submit`
- `order.flower_art.craft`
- `order.flower_rack.sell`
- `basic.mail.claim`
- `basic.task.claim`
- `union.build`
- `activity.claim`

### 6. Scheduler：可解释调度

替换零散 timer 和顺序分支：

- 快速土地循环。
- 领域同步循环。
- 领奖循环。
- 必要的状态刷新循环。
- 失败显式记录，不用隐藏式长退避掩盖协议问题。

调度器需要能告诉 UI 某个领域为什么等待：

- 未观察到必要 namespace。
- 缺原材料。
- 缺花瓶。
- 水滴不足。
- 达到日上限。
- 冷却中。
- 资源硬前置校验未通过。
- 暂无 executor。

## 自动化策略

### 任务优先种植

全自动种植优先级建议：

1. 启用任务中有明确截止或高价值的需求。
2. 居民订单缺口。
3. 顾客订单直接花朵缺口。
4. 顾客订单花艺配方缺口。
5. 主线任务缺口。
6. 公会、活动、每周任务等特殊缺口。
7. 低库存 / 高价值 / 自选兜底模式。

打分因素：

- 需求来源优先级。
- 缺口数量。
- 这批作物是否能让下游动作立刻可执行。
- 成长时间和水滴成本。
- 是否已完成培育。
- 当前库存和账本分配后的可用量。

### 居民订单

居民订单策略应简单、稳定：

- 已满足则交付。
- 不满足则生成花朵需求。
- 已达到日限制则暂停。
- 广告位订单或特殊形态需要明确状态，不要误判为空订单。

### 顾客订单

顾客订单要以链路方式处理：

1. 解析订单。
2. 区分直接花朵需求和花艺成品需求。
3. 若成品库存足够，分配并交付。
4. 若成品不足，查 `FlowerArtRecipeByID`。
5. 检查花瓶能力、配方花朵培育状态、花朵库存和账本可用量。
6. 花朵不足则生成种植需求。
7. 花瓶未解锁则标记 blocked。
8. 材料足够则制作。
9. 制作后重新评估订单并交付。

### 花架售卖

花架售卖只能消费“未被更高优先级目标分配”的花艺：

- 优先上架已有成品。
- 不要上架顾客订单需要的成品。
- 制作花架花艺时也要避开居民/顾客/任务已分配的花朵。
- 售卖策略可以保留高价值优先，但必须服从账本分配。

## Web UI 计划

### 账号总览

- 登录状态、WebSocket 状态、最近同步时间。
- 当前水滴、金币、等级、VIP、钻石。
- 自动化启停和运行健康。
- 最近错误和失败原因。

### 目标看板

- 启用目标列表。
- 每个目标的需求、缺口、阻塞原因。
- 任务优先级拖拽或排序。
- 一键查看“为什么现在没做这个任务”。

### 生产队列

- 待种植。
- 待浇水。
- 待收获。
- 待制作花艺。
- 待上架。
- 待交付。
- 待领奖。

### 策略编辑器

- 基础开关。
- 每个领域的优先级。
- 日上限。
- 种植批量、水滴保留线和低库存水位。
- 兜底种植模式。
- 高风险动作确认策略。

## 路线图

### Phase 0：基线修复

- 修复当前 `go test ./...` 在 Web UI 静态资源未生成时失败的问题。
- 给 CI 加入明确的 Web build/embed 顺序，或者让 embed 有稳定占位资源。
- 保持当前行为不变，先让主干可验证。

### Phase 1：领域状态补齐

- 建模 namespace `102` 花瓶状态。
- 建模 namespace `106` 花艺制作/分享状态中对自动化有用的部分。
- 为顾客订单、花艺配方、花瓶能力增加查询接口。
- 增加状态层单元测试。

### Phase 2：需求引擎

- 引入 Demand、DemandSource、InventoryLedger。
- 先支持居民订单和顾客订单。
- UI 展示需求缺口和阻塞原因。

### Phase 3：种植策略重构

- 让种植优先服务需求引擎。
- 当前低库存/高价值/自选改为 fallback。
- 增加“任务优先种植队列日志”。

### Phase 4：操作注册表

- 已把土地操作、居民订单、顾客订单、宫廷订单、组团订单、花艺制作、花架上架和基础领奖纳入统一 Operation/registry 路径。
- 后续新增执行器继续登记 operation spec；runner 不再承载领域决策。

### Phase 5：调度器和解释能力

- 引入多队列调度。
- 移除隐藏式长退避。
- 所有跳过动作都记录 skip reason 或 blocked reason。

### Phase 6：扩展自动化

- 主线任务。
- 每日/每周任务。
- 公会任务。
- 宫廷订单。
- 活动任务。
- 商城/珍珠/福利等高风险自动化，必须先有明确协议和单项授权。

## 第一阶段建议切片

优先做一个能真实改善体验、又不会一次性炸开全项目的切片：

1. 修复测试基线。
2. 建模花瓶状态 namespace `102`。
3. 增加 `FlowerArtAvailability` 查询：等级、花瓶、花朵库存、账本缺口。
4. 顾客订单需求展开为完整链路：成品 -> 配方 -> 花朵 -> 花瓶。
5. 种植策略优先服务顾客订单花艺缺口。
6. 花架售卖尊重顾客订单账本分配。

做完这一片后，系统就会从“能偶尔制作花艺”进化为“知道为什么要制作花艺，并能反向驱动种植”。
