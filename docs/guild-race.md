# 公会竞赛实现说明

本文记录公会竞赛当前仍需长期维护的状态同步、任务选择和错误恢复约束。历史实施步骤、临时提交命令和已经完成的检查清单不在仓库中长期保留。

协议行为以 `internal/babigame/doc.go` 和实际观测为准；实现与测试以以下位置为准：

- `internal/state/fml.go`：namespace 25 状态解析、已接任务补全与任务池新鲜度
- `internal/automation/shop_union.go`：同步、接取、完成、放弃、升级和删除的规划逻辑
- `internal/runner/operation_events.go`：服务端拒绝后的软恢复
- `internal/automation/shop_union_race_test.go`、`internal/state/fml_race_test.go`、`internal/runner/race_tips1_test.go`：行为回归测试

## 状态与同步

- `fmlRace.enter` 用于获取竞赛批次和段位等基础状态；活动批次内再通过 `fmlRace.getTaskList` 获取任务池和已接任务。
- 非竞赛期间（上一批次 `status==2`，或已发布但未开赛的 `status==0` 窗口）不会一直空转：观测到的周赛窗口为每周二 09:00 至周日 21:00（Asia/Shanghai）。窗口一到点立即再 `enter`，成功后下一轮拉任务池。已发布的 `startTime` 先于日历开赛时，等到 `startTime` 再进入。开赛后若批次仍未激活，30 秒重试一次。
- namespace 25 字段 114 成功应用后，状态层设置 `TasksObserved`，并以本地毫秒时间更新 `TasksSyncedAtMs`。Web 端据此展示上次更新时间。
- 首次未观察到任务池、种植收获任务缺少花卉参数，或错误恢复将任务池标记为未观察时，下一轮优先重新拉取任务池。
- 已观察任务池在空闲时每 10 分钟刷新一次。`giveUp`、`finish`、`take` 优先于定时刷新；存在 45 秒内即将可接、且通过其他接取条件的 CD 任务时，刷新会延后，避免换掉即将可接的任务。更远的 CD 不阻止刷新，以便及时发现任务被接取或升级。
- 本地收获计数已达目标但服务端进度仍滞后时，会以 30 秒为最小间隔重新同步。完整任务池仍是权威结果；若同步后服务端计数仍不足，本地高水位会回落，避免持续空转。

## 种植与自主补种

- 进行中的种植收获任务仍优先占用空地（按产量缺口计算竞赛种植格数）。
- 开启普通「自动种植」时，竞赛种够后的剩余空地会继续走自主补种（库存最低）；关闭自动种植时，竞赛只驱动自己的种植/浇水/收获，剩余空地保持空闲。
- 已接种植收获任务已过期时，在 `getTaskList` 清掉该持有前仍冻结自主补种，避免过期任务意外填满田地。

## 接取判定与 UI 原因

`RaceTakeSkipReason` 是自动接取筛选和 UI `take_skip_reason` 的共同入口。空字符串表示任务可进入候选集；非空字符串表示一个最高优先级的不可接原因。

判定顺序如下：

1. 任务已有非零 `UID`：`已被接取`。
2. `AppearTime` 超出 300 毫秒抢先接取窗口：若其他条件允许，显示 `冷却中，HH:mm:ss 后可接`；否则显示 `HH:mm:ss 后刷新`。
3. 分数小于或等于策略下限：`分数不足（≤N）`。
4. 策略只接升级任务，但当前任务未升级：`仅接已升级任务`。
5. 策略排除他人升级任务，且升级者不是当前账号：`他人已升级`。
6. 任务类型优先级不大于 0：`优先级为0`。
7. 任务类型尚无自动完成适配：`暂不支持自动完成`。
8. 种植收获任务缺少目标花卉或花卉尚未培养：`目标花卉未培养`。
9. 顾客订单任务所依赖的顾客订单模块未开启：`顾客订单模块未开启`。
10. 珍珠采集雇佣任务所依赖的安全雇佣劳工未开启：`珍珠雇佣模块未开启`。
11. 花种培育任务分数不是 36：`仅接36分花种培育`（目录升级终点分；非 36 分一律不接）。接取不要求开启鲜花培育模块；竞赛**不主动推进**培育，只接取并在 `FinishCnt` 达标后提交。
12. 花种培育任务已有进度（`FinishCnt > 0`）：`仅接进度为0的花种培育`。

花艺制作（3034）与花艺售卖（3030）均不检查花艺「自动制作 / 自动上架」开关：竞赛自动完成会自行发出 `flowerArt.makeFlowerArt` / `flowerRack.sell`。

- 制作：只选「配方内每朵花都已培养有种子」且 `sPrice` 最高的配方。
- 售卖：缺成品时按同样规则先制作；花架可领时先领取；上架满 5 分钟且尚未到售完领取时间的格子会全部 `cancelSell` 后再挂，以持续推进竞赛进度。上架成品时选库存数量最多的可售花艺（花瓶已解锁）。

候选任务先选已经可接的任务，再选 300 毫秒窗口内的 CD 任务；同组按任务类型优先级降序、分数降序排列。决策循环会在最早可接 CD 的 `AppearTime - 300ms` 醒来，避免默认 4 秒规划间隔错过抢先窗口。UI 直接展示服务端计算出的原因，不应在前端复制一套筛选规则。

## 已接任务自动放弃

开启「自动完成」后，未完成的已接任务会按 `raceTakenAbandonReason` 决定是否 `giveUp`：

1. **花种培育且分数为 36**：一旦已接取则绝不放弃（含手动接取、优先级为 0、模块关闭、分数低于 `min_task_score`、任务池缺行）。竞赛不驱动培育进度，只同步并提交。
2. 其它类型：分数已知且 `Score <= min_task_score`（已接记录缺分数时回退任务池同行）→ 放弃，**即使已有进度**。
3. 花种培育分数已知且不是 36 → 放弃。
4. 种植收获无法完成，或顾客订单 / 珍珠雇佣模块关闭 → 放弃（花种培育 / 花艺制作/售卖不因普通培育或花艺开关关闭而放弃）。
5. 任务类型优先级为 0 → 放弃。
6. 任务池已观察但找不到当前 `TaskMsId`，且 `FinishCnt==0` → 放弃；有进度时保留，避免同步缺口误弃。

分数仍为 0（任务池与已接都未解析出分数）时，不会因分数门槛放弃，但会暂停种植推进，直到分数落地或其它放弃条件成立。

## 已接任务与软恢复

- namespace 25 字段 110 是账号竞赛记录的主要来源；任务池中 `UID == roleID` 的行用于补全或纠正已接任务。完整任务池不再包含该任务实例时，状态层会清理孤立的已接任务。
- 字段 110 的稀疏增量（常见于 `giveUpTask`，往往只有 `giveUpTime`/`uTime`）不得把缺省的 `fTaskNum`/`buyTaskNum` 当成 0；否则 UI「已做」会被清零。只有 JSON 显式带上对应字段时才更新配额计数。
- `enter` / `getTaskList` 通常不带回字段 110。重启后若配额尚未观察，会调用 `fmlRace.getFmlRaceUsrRankList`，从 namespace 25 字段 116（成员榜 `IFmlRaceUsrRcd[]`）恢复当前账号的 `fTaskNum`。
- 从任务池补出的任务若 `TargetCnt` 或 `FinishCnt` 未知，必须按未完成处理，不得以 `0/0` 自动提交。
- 顾客订单 / 珍珠雇佣进度同步仅在对应业务模块开启时触发（模块关闭会放弃任务）。花艺制作/售卖由竞赛自行驱动并同步。花种培育只接取与提交：定期 `getTaskList` 刷新 `FinishCnt`，达标后 `finishTask`，不发出培育类 RPC。
- 自动完成开启时，已接但尚未完成的任务若分数不高于当前下限、优先级变为 0，或已无法由启用模块完成，会自动放弃；任务池暂时缺行只会在尚无进度时触发放弃，避免误丢已有进度的任务。
- `takeTask` 返回 `codeOfLangJs == "fmlRace_tips1"` 时，表示账号已经接取其他任务。Runner 将其作为可恢复状态：不把账号标记为异常，保留当前快照并把任务池标记为未观察，使下一轮重新同步。
- `takeTask` 返回“任务冷却中”时，Runner 按任务的 `AppearTime` 加短暂缓冲等待，并保留当前任务池，使下一拍直接重试接取，避免把抢先窗口消耗在 `getTaskList` 上。
- 服务端提示任务已被其他成员接取时，先在本地把对应任务行标记为已接，再触发重新同步，避免同步前重复选择同一行。
- 服务端提示接取次数达到上限时，本批次设置粘性的配额耗尽状态并重新同步，避免反复发送必然失败的请求。

## 维护原则

- 新增或调整接取门禁时，同时更新 `RaceTakeSkipReason`、对应表驱动测试和本文的原因顺序。
- 花种培育（3044）硬编码只接分数 36 且 `FinishCnt==0`；接取不依赖鲜花培育模块；竞赛不主动推进培育。改此规则时同步常量 `raceFlowerCultivateRequiredScore`、放弃文案和本文。
- 调整任务池刷新节奏时，同时更新 Go 常量、Web 展示文案和相关测试。
- 一次性实施计划在功能完成后删除；只有解释当前行为、协议约束或长期维护决策的文档留在仓库中。
