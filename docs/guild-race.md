# 公会竞赛实现说明

本文记录公会竞赛当前仍需长期维护的状态同步、任务选择和错误恢复约束。历史实施步骤、临时提交命令和已经完成的检查清单不在仓库中长期保留。

协议行为以 `internal/babigame/doc.go` 和实际观测为准；实现与测试以以下位置为准：

- `internal/state/fml.go`：namespace 25 状态解析、已接任务补全与任务池新鲜度
- `internal/automation/shop_union.go`：同步、接取、完成、放弃、升级和删除的规划逻辑
- `internal/runner/operation_events.go`：服务端拒绝后的软恢复
- `internal/automation/shop_union_race_test.go`、`internal/state/fml_race_test.go`、`internal/runner/race_tips1_test.go`：行为回归测试

## 状态与同步

- `fmlRace.enter` 用于获取竞赛批次和段位等基础状态；活动批次内再通过 `fmlRace.getTaskList` 获取任务池和已接任务。
- namespace 25 字段 114 成功应用后，状态层设置 `TasksObserved`，并以本地毫秒时间更新 `TasksSyncedAtMs`。Web 端据此展示上次更新时间。
- 首次未观察到任务池、种植收获任务缺少花卉参数，或错误恢复将任务池标记为未观察时，下一轮优先重新拉取任务池。
- 已观察任务池在空闲时每 10 分钟刷新一次。`giveUp`、`finish`、`take` 优先于定时刷新；存在 10 分钟内即将可接、且通过其他接取条件的 CD 任务时，刷新会延后，避免换掉即将可接的任务。
- 本地收获计数已达目标但服务端进度仍滞后时，会以 30 秒为最小间隔重新同步。完整任务池仍是权威结果；若同步后服务端计数仍不足，本地高水位会回落，避免持续空转。

## 接取判定与 UI 原因

`RaceTakeSkipReason` 是自动接取筛选和 UI `take_skip_reason` 的共同入口。空字符串表示任务可进入候选集；非空字符串表示一个最高优先级的不可接原因。

判定顺序如下：

1. 任务已有非零 `UID`：`已被接取`。
2. `AppearTime` 超出 4 秒抢先接取窗口：若其他条件允许，显示 `冷却中，HH:mm 后可接`；否则显示 `HH:mm 后刷新`。
3. 分数小于或等于策略下限：`分数不足（≤N）`。
4. 策略只接升级任务，但当前任务未升级：`仅接已升级任务`。
5. 策略排除他人升级任务，且升级者不是当前账号：`他人已升级`。
6. 任务类型优先级不大于 0：`优先级为0`。
7. 任务类型尚无自动完成适配：`暂不支持自动完成`。
8. 种植收获任务缺少目标花卉或花卉尚未培养：`目标花卉未培养`。
9. 顾客订单任务所依赖的顾客订单模块未开启：`顾客订单模块未开启`。

候选任务先选已经可接的任务，再选 4 秒窗口内的 CD 任务；同组按任务类型优先级降序、分数降序排列。UI 直接展示服务端计算出的原因，不应在前端复制一套筛选规则。

## 已接任务与软恢复

- namespace 25 字段 110 是账号竞赛记录的主要来源；任务池中 `UID == roleID` 的行用于补全或纠正已接任务。完整任务池不再包含该任务实例时，状态层会清理孤立的已接任务。
- 从任务池补出的任务若 `TargetCnt` 或 `FinishCnt` 未知，必须按未完成处理，不得以 `0/0` 自动提交。
- `takeTask` 返回 `codeOfLangJs == "fmlRace_tips1"` 时，表示账号已经接取其他任务。Runner 将其作为可恢复状态：不把账号标记为异常，保留当前快照并把任务池标记为未观察，使下一轮重新同步。
- 服务端提示任务已被其他成员接取时，先在本地把对应任务行标记为已接，再触发重新同步，避免同步前重复选择同一行。
- 服务端提示接取次数达到上限时，本批次设置粘性的配额耗尽状态并重新同步，避免反复发送必然失败的请求。

## 维护原则

- 新增或调整接取门禁时，同时更新 `RaceTakeSkipReason`、对应表驱动测试和本文的原因顺序。
- 调整任务池刷新节奏时，同时更新 Go 常量、Web 展示文案和相关测试。
- 一次性实施计划在功能完成后删除；只有解释当前行为、协议约束或长期维护决策的文档留在仓库中。
